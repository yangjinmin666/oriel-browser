# BOSS 直聘（zhipin.com）

## ⚠️ 第一条：匿名浏览器进不去，必须用已登录的真实浏览器

2026-07-28 实测三种情况：

| 环境 | 结果 |
|---|---|
| 无头 Chrome（全新 profile） | **被重定向到 `/web/passport/zp/security.html`**，标题「请稍候」，正文 51 字符 |
| 有头 Chrome（全新 profile） | 留在岗位页，但正文 0 字符、**0 个岗位卡片** |
| 有头 + 已登录会话（真实日常浏览器） | 正常，15 个岗位卡片，`loggedIn: true` |

**结论：BOSS 直聘比知乎严格得多。** 知乎只是给无头浏览器返回白页；BOSS 直聘会主动把你踢到安全验证页，而且**即使有头，全新的匿名 profile 也拿不到岗位列表**。

所以访问 BOSS 直聘必须满足：

1. **有头模式**（`headless: false`）
2. **已登录的会话**，优先连接用户日常已登录浏览器
3. 页面是单页应用且渲染慢，**至少等 12 秒**再读 DOM，不要 3 秒就下结论

如果读到的是 `/web/passport/zp/security.html` 或者正文极短，**那不是没加载完，是被反爬拦了**。再等没用，换满足上面三条的环境重试。

## 搜索列表页（已实测）

搜索列表页：`https://www.zhipin.com/web/geek/jobs?query=<关键词>&city=<城市码>`

- 城市码示例：上海 `101020100`
- 有头、已登录、等待 13 秒后，测试查询得到 **15 张** `.job-card-box` 岗位卡片。

| 选择器 | 内容 | 实测说明 |
|---|---|---|
| `.job-card-box` | 岗位卡片容器 | 本次页面 15 个 |
| `.job-name` | 岗位名 | 已验证 |
| `.job-salary` | 列表薪资 | 常读到 `-K`，数字缺失时必须标记「未获取」 |
| `.tag-list` | 经验、学历等标签 | 已验证 |
| `.boss-name` | **公司名** | 类名会骗人，内容不是招聘人姓名 |
| `.company-location` | 地点 | 已验证 |
| `.job-card-box a[href*="job_detail"]` | 岗位详情链接 | 已验证，链接形如 `/job_detail/*.html` |

列表容器：`.job-list-container`、`.rec-job-list`。

### 加载更多的实测结论

在上述列表页连续两次向下滚动（每次 2200px，间隔 1.8 秒）后，岗位卡片仍为 15 张、页面高度不变，也未发现可见的分页控件。**本次查询没有观察到自动加载更多。** 这不是对所有关键词、城市或登录状态的全局结论；翻页和更多加载方式仍待逐页验证。

## 岗位详情页（已实测）

测试页形如：`https://www.zhipin.com/job_detail/*.html`。在有头、已登录会话中等待 13 秒后，以下选择器在真实详情页存在：

| 选择器 | 内容 | 实测结果 |
|---|---|---|
| `h1` | 岗位标题 | 1 个 |
| `.job-title` | 岗位标题 | 1 个，与页面标题区域对应 |
| `.job-primary .salary` | 详情页薪资 | 1 个；不要使用宽泛的 `.salary`，它会命中相似职位等区域 |
| `.job-location` | 工作地点 | 1 个 |
| `.job-primary .job-tags` | 经验、学历等岗位标签 | 2 个 |
| `.job-boss-info` | 招聘方信息区域 | 1 个 |
| `.job-detail` | 岗位详情主容器 | 1 个 |
| `.job-detail .job-detail-section` | 详情分段 | 7 个；第一个分段含「职位描述」 |
| `.job-detail-company` | 公司介绍与工商等信息容器 | 1 个 |

### 打招呼入口：只识别，不点击

详情页有两个可见的「立即沟通」入口，均为：

```text
a.btn.btn-startchat[href="javascript:;"]
```

`.btn-startchat` 与 `.btn-startchat-wrap` 在测试页各命中 2 个。它们不是普通跳转链接，**禁止把 `href` 当作聊天页 URL**，也禁止自动点击。

## ⚠️ 投递（打招呼）请谨慎，这是账号风险

**读岗位和投递岗位，风险完全不是一个量级。**

- **搜索、筛选、整理候选岗位**：只读页面，风险低，适合自动化。
- **打招呼、投递、发送消息**：BOSS 直聘对异常行为查得严。短时间大量操作可能被判定为机器行为，后果包括限制沟通、限流，甚至封号。

因此建议：

1. 自动完成**搜索 → 筛选 → 排序 → 输出候选清单**。
2. 投递必须保留**人工确认**；不要在只读工具或搜索工具中夹带打招呼。
3. 即使用户确认操作，也应严格限速、少量执行，不要使用同一模板批量发送。
4. 不要提供「一次性投递 100 个岗位」这类能力。

## 未验证的部分

以下没有实测，不能当作既有能力或稳定选择器：

- 点击 `.btn-startchat` 后的实际结果：是否弹窗、跳转聊天页、要求验证码，均**未验证**。本次为了保护用户求职账号，未点击该控件。
- 「已沟通」「继续沟通」等重复沟通状态的文案、DOM 选择器和判断规则，均**未验证**。
- 列表的分页、无限滚动和「加载更多」在其他查询条件下的行为，**未验证**；本次仅观察到两次滚动后没有新增卡片。
- 筛选器（薪资、经验、公司规模）的选择器和交互方式，**未验证**。

## 登录

可先登录一次，让浏览器持久保存登录态：

```bash
node host-shim/login.mjs https://www.zhipin.com/web/user/?ka=header-login
```

或用 `connectTo` 模式连接用户日常已登录的浏览器。后者对反爬通过率更高，但需要浏览器开着仅本机可访问的调试端口，且必须遵守：只创建和关闭自动化自己的标签页，不触碰用户原有标签页或浏览器进程。

注意：ego lite 0.4.5.6 的站点知识加载器目前空转，不能依赖 `learnContext()` 自动发现这份知识；现阶段请直接读取本说明书。

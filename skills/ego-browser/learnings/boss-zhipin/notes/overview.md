# BOSS 直聘（zhipin.com）

## ⚠️ 第一条：匿名浏览器进不去，必须用已登录的真实浏览器

2026-07-28 实测三种情况：

| 环境 | 结果 |
|---|---|
| 无头 Chrome（全新 profile） | **被重定向到 `/web/passport/zp/security.html`**，标题「请稍候」，正文 51 字符 |
| 有头 Chrome（全新 profile） | 留在岗位页，但正文 0 字符、**0 个岗位卡片** |
| 有头 + 已登录会话（真实日常浏览器） | 正常，15 个岗位卡片，`loggedIn: true` |

**结论：BOSS 直聘比知乎严格得多。** 知乎只是给无头浏览器返回白页；BOSS 直聘会主动把你踢到安全验证页，而且**即使有头，全新的匿名 profile 也拿不到岗位列表**。

所以访问 BOSS 直聘必须满足：

1. **有头模式**（`headless: false`）
2. **已登录的会话** —— 先登录一次，让浏览器持久保存登录态
3. 页面是单页应用且渲染慢，**至少等 12 秒**再读 DOM，不要 3 秒就下结论

如果读到的是 `/web/passport/zp/security.html` 或者正文极短，**那不是没加载完，是被反爬拦了**。再等没用，换满足上面三条的环境重试。

## 页面结构（已实测）

搜索列表页：`https://www.zhipin.com/web/geek/jobs?query=<关键词>&city=<城市码>`

- 城市码示例：上海 `101020100`

岗位卡片，**一页 15 个**：

| 选择器 | 内容 | 实测样例 |
|---|---|---|
| `.job-card-box` | 卡片容器 | —— |
| `.job-name` | 岗位名 | 产品经理 |
| `.job-salary` | 薪资 | `-K`（见下面的坑） |
| `.tag-list` | 经验 + 学历 | 经验不限 初中及以下 |
| `.boss-name` | **公司名** | 上海寰轮实业有限公司 |
| `.company-location` | 地点 | 上海·浦东新区·陆家嘴 |
| `.job-card-box a[href]` | 详情链接 | `/job_detail/xxx.html` |

列表容器：`.job-list-container`、`.rec-job-list`

## 两个会骗人的地方

**1. `.boss-name` 里是公司名，不是招聘人姓名。** 类名叫 boss，内容却是公司。别照类名理解。

**2. `.job-salary` 经常读到 `-K`，数字缺失。** 实测就是这样。可能是延迟渲染，也可能该岗位薪资面议。**不要把 `-K` 当成真实薪资写进结果**，遇到就标记为「未获取」，需要准确薪资时进详情页看。

## ⚠️ 投递（打招呼）请谨慎，这是账号风险

**读岗位和投递岗位，风险完全不是一个量级。**

- **筛选岗位**：只读页面，风险低，适合全自动
- **批量打招呼**：BOSS 直聘对异常行为查得很严。短时间内大量打招呼容易被判定为机器行为，后果可能是限制打招呼、限流、甚至封号。**这是用户自己的求职账号，出问题代价很大。**

所以自动化流程建议这么设计：

1. 自动完成**搜索 → 筛选 → 排序 → 输出候选清单**
2. 投递环节**保留人工确认**，或者严格限速（比如每次只投几个、之间留足间隔）
3. 打招呼内容不要千篇一律的模板 —— 一样的开场白既容易被平台识别，HR 也会直接忽略

不要写「一次性投递 100 个岗位」这种工具。

## 登录

先登录一次，之后持久有效：

```bash
node host-shim/login.mjs https://www.zhipin.com/web/user/?ka=header-login
```

或者用连接模式接到用户日常已登录的浏览器（反爬通过率最高，但需要该浏览器开着调试端口，且与用户共享浏览器）。
